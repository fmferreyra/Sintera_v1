Estamos desarrollando una plataforma tipo CRM basado en redmine. La idea es poder realizar modificaciones, visualizarlas de manera local y una vez que validemos que 
todo funciona correctamente subirlas al repositorio.

En caso de eliminar el contenedor completo, la plataforma debe poder levantarse nuevamente en un nuevo contenedor docker y funcionar exactamente igual.

Para modificar cualquier archivo, directorio, codigo de este repositorio se debe tener en cuenta la estructura mencionada abajo. Esto es porque el proyecto debe mantenerse facil de modificar y escalar. Adaptando tanto diseños, plugins e integraciones futuras.
Todas las modificaciones realizadas deben poder persistir facilmente o adaptarse en caso de una actualizacion de la version de Redmine.
El repositorio tiene que quedar listo para poder instalar docker en cualquier servidor y montar la plataforma tal cual la visualizabamos de manera local. Mateniendo siempre la vistas, estilos, estructura html, scripts, plugins, etc.
La plataforma debe cumplir con estandares de calidad y seguridad de la informacion.
Ademas debe mantener la estructura necesaria para poder actualizar la version de Redmine.
Siempre debe mantener diseño responsive respetando colores, fuentes y formas.
Ademas, en caso de que el cliente posea un dominio registrado, la plataforma debera ser capaz de adaptarse a ese dominio con https. En caso de que el cliente prefiera ingresar solo con la ip del servidor debe poder hacerlo tranquilamente.

La plataforma debe mantener una identidad propia, para que la plataforma no se parezca a redmine. Debe tener personalidad de Sintera.

1. Redmine

El container:

redmine:7.0.0

es nuestra aplicación.

En desarrollo y en instalaciones sin dominio, Sintera queda accesible mediante el proxy Caddy en:

http://localhost:3000

El contenedor de Redmine no publica ningún puerto directamente. Caddy recibe las solicitudes y las reenvía internamente a `app:3000`. En producción, el puerto publicado se configura en `.env`: `3000` para acceso por IP o `80/443` para un dominio con HTTPS.

Más adelante será Sintera.

2. PostgreSQL

El segundo container:

postgres:14

es exclusivamente la base de datos.

No publicamos:

5432

hacia Windows.

Por lo tanto, PostgreSQL solamente es accesible desde la red interna de Docker:

Redmine → db:5432 → PostgreSQL

Eso es bueno desde el punto de vista de seguridad.

Persistencia

Los containers son desechables.

Los datos no.

Tenemos dos Docker volumes:

sintera_postgres_data
        │
        └── base de datos


sintera_redmine_files
        │
        └── archivos/adjuntos de Redmine

Por eso:

docker compose down
docker compose up -d

puede destruir y recrear los containers sin destruir los datos.

En cambio:

docker compose down -v

sí elimina los volúmenes, por lo que en producción será un comando que prácticamente nunca deberemos utilizar sin una razón explícita.

Redmine será el motor que nosotros aprovechamos, pero el cliente debe percibir Sintera como el producto.

Y cuando llegue una actualización de Redmine, queremos poder hacer:

Sintera 1.0
   │
   ├── Theme Sintera
   ├── Plugin Sintera
   └── Redmine 7.0.x

y posteriormente:

Sintera 1.1
   │
   ├── Theme Sintera
   ├── Plugin Sintera
   └── Redmine 7.0.y

sin haber construido todo sobre modificaciones irreversibles del código de Redmine.
